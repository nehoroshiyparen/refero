# Refero (SciFlow)

**Платформа для управления научными статьями и рецензирования**

Refero реализует полный жизненный цикл научной публикации: от создания черновика и совместной работы с соавторами до прохождения рецензирования и финальной публикации. Система спроектирована для исследовательских групп, журналов и независимых авторов, которым нужен структурированный и воспроизводимый процесс подготовки статей.

## Возможности

### Аутентификация и управление пользователями

Полный цикл управления учётными записями с поддержкой ролевой модели и безопасным хранением учётных данных.

- **Регистрация и вход** — создание аккаунта с верификацией данных, аутентификация по email и паролю. Пароли хешируются с помощью bcrypt.
- **Обновление токенов** — автоматическое продление сессии через refresh-токен, передаваемый в httpOnly cookie (защита от XSS).
- **Ролевая модель** — пользователь может иметь несколько ролей через таблицу `user_roles`:
  - `AUTHOR` — создание и редактирование статей, управление соавторами, просмотр рецензий.
  - `REVIEWER` — управление рецензиями, просмотр назначенных статей.
  - `ADMIN` — полный доступ, управление журналами и модерация.
- **Профиль пользователя** — личный кабинет с созданием профилей автора (организация, должность, ORCID, био) и рецензента (специализация, степень).
- **Публичные профили** — просмотр профилей других пользователей с их опубликованными статьями.

### Статьи

Центральный модуль системы, обеспечивающий полный цикл работы с научными статьями — от черновика до публикации.

- **Создание и редактирование** — автор создаёт статью, указывая заголовок, аннотацию, ключевые слова, язык и журнал.
- **Версионирование** — каждая статья может иметь несколько версий с независимым статусом. Автор управляет, какая версия является текущей.
- **Управление соавторами** — добавление и удаление соавторов из числа зарегистрированных пользователей.
- **Согласование соавторами** — отправка версии на согласование: каждый соавтор подтверждает или отклоняет. При повторной отправке предыдущие решения сбрасываются.
- **Назначение рецензента** — после согласования всех соавторов система случайным образом назначает рецензента из пользователей с ролью `REVIEWER`.
- **Скрытие и показ статьи** — автор может временно скрыть статью из общего доступа.
- **Фильтрация и поиск** — статус, журнал, язык, автор, ключевые слова, полнотекстовый поиск.
- **Счётчик просмотров** — учитывается через отдельный эндпоинт для защиты от кэширования.

### Рецензирование

Модуль для организации процесса экспертной оценки статей.

- **Назначение рецензента** — автоматический выбор случайного рецензента для версии, прошедшей согласование. При повторной отправке на рецензирование старый ассигнмент с выполненным ревью удаляется и создаётся новый.
- **Статусы рецензии**:
  - `PENDING` — ожидание решения;
  - `APPROVED` — статья одобрена;
  - `REJECTED` — статья отклонена;
  - `REQUESTING_CHANGES` — запрошены исправления.
- **Комментарии рецензента** — построчная лента комментариев к версии статьи.
- **Просмотр рецензий** — рецензент видит все свои назначения, автор — рецензии на свои статьи.
- **Страница просмотра версии** — все авторизованные пользователи могут просматривать содержимое версии, решение рецензента, комментарии и статусы согласования соавторов.

### Журналы

Модуль управления научными журналами.

- **CRUD для журналов** — доступно только `ADMIN`.
- **Привязка статей** — при создании или редактировании статьи автор указывает журнал.

### Цитирования

Модуль для отслеживания цитируемости научных статей внутри платформы.

### Команды Make

Проект включает Makefile с набором команд для типовых операций. Каждая команда — это алиас для соответствующей Docker Compose инструкции, что избавляет от запоминания длинных команд.

| Команда          | Описание                                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make start`     | Запустить все сервисы в фоновом режиме (`docker compose up -d`). Поднимает backend, frontend, PostgreSQL и другие контейнеры, описанные в `docker-compose.yml`.                                                                     |
| `make stop`      | Остановить все запущенные сервисы (`docker compose down`). Контейнеры останавливаются, но данные в volumes сохраняются.                                                                                                             |
| `make logs`      | Вывести логи всех контейнеров в реальном времени (`docker compose logs -f`). Удобно для отладки — показывает объединённый поток логов backend, frontend и БД. Нажмите `Ctrl+C` для выхода.                                          |
| `make rebuild`   | Полная пересборка с нуля: останавливает контейнеры, удаляет volumes (сбрасывает БД), пересобирает образы и запускает сервисы. Используйте, если нужно полностью очистить состояние или после значительных изменений в конфигурации. |
| `make bash-back` | Открыть интерактивную shell-сессию внутри контейнера backend (`docker compose exec backend bash`). Полезно для ручного запуска миграций, отладки, проверки файлов и выполнения произвольных команд внутри окружения контейнера.     |

### Миграции базы данных

Управление схемой БД осуществляется через **Alembic**. Миграции выполняются автоматически при старте backend-контейнера (см. `command` в `docker-compose.yml`), но при необходимости их можно запустить вручную.

В директории `backend/` есть собственный `Makefile` с командами для миграций:

```bash
cd backend

# Накатить все миграции
make migrate

# Откатить последнюю миграцию
make downgrade

# Создать новую миграцию (после изменений в моделях)
make makemigrations m="описание изменений"

# Просмотреть историю миграций
make history
```

Либо напрямую через Docker:

```bash
# Накатить все миграции
docker compose exec backend alembic upgrade head

# Откатить последнюю миграцию
docker compose exec backend alembic downgrade -1

# Создать новую миграцию
docker compose exec backend alembic revision --autogenerate -m "описание изменений"

# Просмотреть историю миграций
docker compose exec backend alembic history
```

Миграции находятся в `backend/alembic/versions/`. Новые файлы создаются автоматически при выполнении `alembic revision --autogenerate`, который сравнивает текущее состояние моделей с реальной схемой БД.

## API

Все эндпоинты API находятся под префиксом `/api`. Система следует REST-конвенции: `GET` для чтения, `POST` для создания, `PUT`/`PATCH` для обновления, `DELETE` для удаления.

| Модуль    | Префикс          | Описание                                                    |
| --------- | ---------------- | ----------------------------------------------------------- |
| Auth      | `/api/auth`      | Регистрация, вход, выход, обновление токенов                |
| Users     | `/api/users`     | Просмотр и редактирование профилей, список пользователей    |
| Articles  | `/api/articles`  | CRUD статей, управление соавторами, загрузка/скачивание PDF |
| Reviews   | `/api/reviews`   | Создание рецензий, изменение статусов, просмотр рецензий    |
| Journals  | `/api/journals`  | CRUD журналов (доступно только ADMIN)                       |
| Citations | `/api/citations` | Подсчёт цитирований, управление ссылками                    |

Детальная документация с примерами запросов и ответов доступна в **Swagger UI** по адресу `http://localhost:8000/docs` после запуска проекта.

## Архитектура

### Backend

Проект следует слоистой архитектуре **Repository → Service → Router**, где каждый слой имеет чёткую зону ответственности:

- **Repository** — взаимодействие с базой данных через SQLAlchemy. Инкапсулирует SQL-запросы и маппинг моделей.
- **Service** — бизнес-логика. Обрабатывает данные, проверяет условия, координирует несколько репозиториев при необходимости.
- **Router** — HTTP-эндпоинты. Валидирует входящие данные через Pydantic-схемы, вызывает сервисы, формирует ответы.

```
backend/
├── app/
│   ├── core/             # Конфигурация, исключения, зависимости, общие схемы ответов
│   ├── infrastructure/   # Настройка базы данных (SQLAlchemy engine, сессии), Alembic
│   └── modules/
│       ├── auth/         # Аутентификация, JWT-токены, хеширование паролей
│       ├── users/        # Пользователи, профили, ролевая модель
│       ├── articles/     # Статьи, соавторы, согласование, загрузка файлов
│       ├── reviews/      # Рецензирование, статусы рецензий
│       ├── journals/     # Управление журналами
│       └── citations/    # Цитирования и метрики
├── tests/                # Тесты на Pytest
└── alembic/              # Миграции базы данных
```

### Frontend

Фронтенд следует методологии **Feature-Sliced Design (FSD)** с разделением на слои:

- **`shared/`** — переиспользуемые утилиты, API-клиент, UI-компоненты (shadcn/ui, Tailwind)
- **`entities/`** — бизнес-сущности: article, review, user, auth, journal, citation (каждая со своим типом, API и хранилищем)
- **`features/`** — пользовательские сценарии (не используются напрямую, логика в pages)
- **`pages/`** — страницы приложения, каждая в своей папке с UI + index.ts
- **`app/`** — инициализация приложения, провайдеры, роутинг

```
frontend/src/
├── shared/
│   ├── api/             # fetch-обёртка с авто-refresh по 401
│   └── ui/              # Header, Button, другие общие компоненты
├── entities/
│   ├── article/         # ArticlePayload, ArticleVersionPayload, API
│   ├── review/          # ReviewAssignment, CommentPayload, API
│   ├── user/            # UserBrief, UserProfile, API
│   ├── auth/            # AccessTokenPayload, AuthProvider
│   ├── journal/         # JournalPayload
│   └── citation/        # Citation types
├── pages/
│   ├── landing/         # Лендинг
│   ├── login/           # Вход
│   ├── register/        # Регистрация
│   ├── articles/        # ArticlesPage, ArticleDetailPage, ReviewPage, и т.д.
│   ├── reviews/         # AssignmentsPage, AssignmentReviewPage
│   └── profile/         # ProfilePage, PublicProfilePage
└── app/
    ├── providers/       # AuthProvider
    └── routes/          # AppRouter (BrowseRouter → Routes)
```

**Ключевые решения фронтенда:**

- **BrowserRouter** (не data-router) — избегает проблем с React 19 concurrent mode.
- **Navigate вместо navigate()** в async-обработчиках — предотвращает race-conditions.
- **fetch-обёртка** с перехватом 401 и авто-refresh, `Cache-Control: no-cache` на всех запросах.
- **User.roles: list** — пользователь может иметь несколько ролей, проверка через `roles.some()`.

## Модель базы данных

Система использует PostgreSQL с 18 таблицами. Ниже — сводка всех моделей и связей между ними.

### Таблицы

| # | Таблица | Назначение | Ключевые связи |
|---|---------|------------|----------------|
| 1 | `users` | Пользователи системы | `created_by`, `article_authors`, `review_assignments` |
| 2 | `roles` | Справочник ролей (GUEST, AUTHOR, REVIEWER, ADMIN) | `user_roles` |
| 3 | `user_roles` | Связь пользователей с ролями (M:N) | `users.id`, `roles.name` |
| 4 | `author_profiles` | Профили авторов (орг., должность, ORCID, био) | `users.id` (1:1) |
| 5 | `reviewer_profiles` | Профили рецензентов (специализация, степень) | `users.id` (1:1) |
| 6 | `articles` | Статьи (метаданные, счётчики, видимость) | `current_version_id`, `creator_id`, `journal_id` |
| 7 | `article_versions` | Версии статей (заголовок, аннотация, PDF, статус) | `articles.id`, `article_statuses.name` |
| 8 | `article_authors` | Соавторы статей (M:N) | `articles.id`, `users.id` |
| 9 | `article_approvals` | Согласование версий соавторами | `article_versions.id`, `users.id`, `approval_statuses.name` |
| 10 | `article_statuses` | Справочник статусов версий (DRAFT, PENDING_APPROVAL, REVIEW, PUBLISHED, REJECTED) | — |
| 11 | `approval_statuses` | Справочник статусов согласования (PENDING, APPROVED, REJECTED) | — |
| 12 | `journals` | Научные журналы | `articles.journal_id` |
| 13 | `citations` | Цитирования между статьями | `articles.id` (citing + cited) |
| 14 | `review_assignments` | Назначения рецензентов на версии | `article_versions.id`, `users.id` (1:1 с версией) |
| 15 | `reviews` | Результаты рецензирования (решение, дата) | `review_assignments.id` (1:1) |
| 16 | `version_comments` | Комментарии рецензентов к версиям | `article_versions.id`, `users.id` |
| 17 | `review_statuses` | Справочник статусов рецензий (PENDING, APPROVED, REJECTED, REQUESTING_CHANGES) | — |
| 18 | `refresh_tokens` | Refresh-токены для аутентификации | `users.id` |

### Схема связей

```
users ──< user_roles >── roles
  │
  ├── author_profile (1:1)
  ├── reviewer_profile (1:1)
  ├── refresh_tokens (1:N)
  ├── created_articles (1:N) ──> articles
  ├── articles_as_author (1:N) ──> article_authors ──> articles
  ├── approvals_given (1:N) ──> article_approvals ──> article_versions ──> articles
  └── review_assignments (1:N) ──> review_assignments ──> article_versions

journals ──< articles (1:N)
articles ──< article_versions (1:N)
articles ──< article_authors (1:N)
articles ──< citations (citing/cited)

article_versions ──< article_approvals (1:N)
article_versions ──< version_comments (1:N)
article_versions ──< review_assignments (1:1)

review_assignments ──< reviews (1:1)
```

### Статусная модель версии

```
DRAFT ──→ PENDING_APPROVAL ──→ REVIEW ──→ PUBLISHED
  ↑                              │
  └──────────────────────────────┘
       (при REQUESTING_CHANGES)
```

### Ключевые особенности

- **Пользователь может иметь несколько ролей** — через junction table `user_roles`.
- **Статья имеет версионирование** — `Article.current_version_id` указывает на активную версию, все версии хранятся в `article_versions`.
- **Рецензирование привязано к версии** — `ReviewAssignment.article_version_id` уникален (одна версия → один рецензент за раз).
- **Лукап-таблицы** (`article_statuses`, `approval_statuses`, `review_statuses`, `roles`) — значения enum хранятся как строки с FK-ссылками для referential integrity.
- **Цитирования двунаправленные** — `Citation.from_article_id` (цитирующая статья) и `Citation.to_article_id` (цитируемая, nullable для внешних ссылок).

## Публикационный workflow

Жизненный цикл статьи в системе проходит через несколько обязательных стадий, каждая из которых управляется определёнными правилами доступа и переходов:

```
Черновик (DRAFT)
  │
  │  Автор добавляет соавторов, загружает PDF,
  │  редактирует метаданные статьи
  │
  ▼
Согласование соавторов (PENDING_APPROVAL)
  │
  │  Каждый соавтор подтверждает или отклоняет
  │  текущую версию статьи. До получения всех
  │  согласий статья не может перейти дальше.
  │
  ▼
Рецензирование (REVIEW)
  │
  │  Рецензенты изучают статью и выносят решение:
  │  одобрить, отклонить или запросить доработку.
  │  При запросе доработки статья возвращается
  │  автору на внесение исправлений.
  │
  ├──→ Опубликовано (PUBLISHED)
  │       Статья доступна для чтения и цитирования
  │       всеми пользователями платформы.
  │
  └──→ Отклонено (REJECTED)
          Статья отклонена по итогам рецензирования.
          Автор может создать новый черновик на основе
          отклонённой статьи.
```
