# Refero (SciFlow)

**Платформа для управления научными статьями и рецензирования**

Refero реализует полный жизненный цикл научной публикации: от создания черновика и совместной работы с соавторами до прохождения рецензирования и финальной публикации. Система спроектирована для исследовательских групп, журналов и независимых авторов, которым нужен структурированный и воспроизводимый процесс подготовки статей.

## Возможности

### Аутентификация и управление пользователями

Полный цикл управления учётными записями с поддержкой ролевой модели и безопасным хранением учётных данных.

- **Регистрация и вход** — создание аккаунта с верификацией данных, аутентификация по email и паролю. Пароли хешируются с помощью bcrypt, что гарантирует устойчивость к brute-force атакам.
- **Выход из системы** — инвалидация текущего access-токена, очистка cookie с refresh-токеном.
- **Обновление токенов** — автоматическое продление сессии через refresh-токен, передаваемый в httpOnly cookie. Это исключает доступ к токену из JavaScript и защищает от XSS-атак.
- **Ролевая модель** — три роли с различными уровнями доступа:
  - `AUTHOR` — создание и редактирование статей, управление соавторами, просмотр рецензий на свои статьи.
  - `REVIEWER` — создание и управление рецензиями, просмотр статей, переданных на рецензирование.
  - `ADMIN` — полный доступ, включая управление журналами и модерацию контента.
- **Профиль пользователя** — просмотр и редактирование личных данных (имя, email, биография, affiliation).

### Статьи

Центральный модуль системы, обеспечивающий полный цикл работы с научными статьями — от черновика до публикации.

- **Создание и редактирование** — автор создаёт статью, указывая заголовок, аннотацию, ключевые слова, язык и журнал. Редактирование доступно только пока статья находится в статусе `DRAFT`.
- **Загрузка и скачивание PDF** — прикрепление файла статьи в формате PDF, скачивание загруженных файлов другими пользователями (с учётом прав доступа).
- **Управление соавторами** — добавление и удаление соавторов из числа зарегистрированных пользователей. Соавторы получают уведомления и могут участвовать в согласовании статьи.
- **Согласование соавторами** — отправка статьи на согласование, в ходе которого каждый соавтор подтверждает или отклоняет текущую версию. Пока все соавторы не дадут согласие, статья не переходит к рецензированию.
- **Скрытие и показ статьи** — автор может временно скрыть статью из общего доступа, не удаляя её. Это полезно при доработке или при необходимости ограничить видимость.
- **Фильтрация и поиск** — статьи можно фильтровать по множеству критериев одновременно:
  - статус (draft, pending_approval, review, published, rejected);
  - журнал;
  - язык статьи;
  - автор;
  - ключевые слова;
  - полнотекстовый поиск по заголовку и аннотации.

### Рецензирование

Модуль для организации процесса экспертной оценки статей, соответствующий стандартам научного рецензирования.

- **Создание рецензии** — рецензент (пользователь с ролью `REVIEWER`) может оставить рецензию только на статью в статусе `REVIEW`. Рецензия включает текстовое заключение и итоговое решение.
- **Статусы рецензии** — каждая рецензия проходит через определённый жизненный цикл:
  - `PENDING` — рецензия создана, ожидается решение;
  - `APPROVED` — статья одобрена, может быть опубликована;
  - `REJECTED` — статья отклонена, автор получает рекомендации по доработке;
  - `REQUESTING_CHANGES` — запрошены исправления, статья возвращается автору на доработку с последующим повторным рецензированием.
- **Отзыв рецензии** — рецензент может отозвать свою рецензию, если она была создана по ошибке или требует переработки.
- **Просмотр рецензий** — два режима просмотра: рецензент видит все свои рецензии, автор — все рецензии на свою статью. Это обеспечивает прозрачность процесса для обеих сторон.

### Журналы

Модуль управления научными журналами, к которым привязываются статьи.

- **Создание и редактирование журналов** — полный CRUD для журналов (создание, просмотр, обновление, удаление). Доступно только пользователям с ролью `ADMIN`.
- **Привязка статей** — при создании или редактировании статьи автор указывает журнал, в котором планируется публикация. Это позволяет группировать статьи по тематическим направлениям.
- **Просмотр журналов** — все пользователи могут просматривать список журналов и привязанные к ним статьи.

### Цитирования

Модуль для отслеживания цитируемости научных статей внутри платформы.

## Установка и запуск

### Требования

Перед началом убедитесь, что на вашей машине установлены:

- **Docker** ≥ 24.0 и **Docker Compose** ≥ 2.20 (входят в Docker Desktop или устанавливаются отдельно)
- **Make** (опционально, но рекомендуется — значительно упрощает работу с командами)
- **Git** — для клонирования репозитория

<details>
<summary>Проверка установленных инструментов</summary>

```bash
# Проверка Docker
docker --version
# Ожидается: Docker version 24.x.x или выше

# Проверка Docker Compose
docker compose version
# Ожидается: Docker Compose version v2.x.x или выше

# Проверка Make
make --version
# Ожидается: GNU Make 4.x или выше

# Проверка Git
git --version
```

Если какой-то инструмент отсутствует, установите его перед продолжением.

</details>

### Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone https://github.com/nehoroshiyparen/refero.git refero
cd refero

# 2. Создать файл окружения из шаблона
cp .env.example .env
# Отредактируйте .env, указав актуальные значения:
#   - SECRET_KEY — секретный ключ для JWT
#   - DATABASE_URL — строка подключения к PostgreSQL
#   - другие параметры при необходимости

# 3. Запустить все сервисы
make start
# Альтернатива без Make: docker compose up -d
```

После запуска доступны следующие сервисы:

| Сервис         | URL                        | Описание                                |

| **Backend**    | http://localhost:7812      | REST API на FastAPI                     |
| **Swagger UI** | http://localhost:7812/docs | Интерактивная документация API          |
| **Frontend**   | http://localhost:5173      | Веб-интерфейс на React + Vite           |

### Команды Make

Проект включает Makefile с набором команд для типовых операций. Каждая команда — это алиас для соответствующей Docker Compose инструкции, что избавляет от запоминания длинных команд.

| Команда          | Описание                                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make start`     | Запустить все сервисы в фоновом режиме (`docker compose up -d`). Поднимает backend, frontend, PostgreSQL и другие контейнеры, описанные в `docker-compose.yml`.                                                                     |
| `make stop`      | Остановить все запущенные сервисы (`docker compose down`). Контейнеры останавливаются, но данные в volumes сохраняются.                                                                                                             |
| `make logs`      | Вывести логи всех контейнеров в реальном времени (`docker compose logs -f`). Удобно для отладки — показывает объединённый поток логов backend, frontend и БД. Нажмите `Ctrl+C` для выхода.                                          |
| `make rebuild`   | Полная пересборка с нуля: останавливает контейнеры, удаляет volumes (сбрасывает БД), пересобирает образы и запускает сервисы. Используйте, если нужно полностью очистить состояние или после значительных изменений в конфигурации. |
| `make bash-back` | Открыть интерактивную shell-сессию внутри контейнера backend (`docker compose exec backend bash`). Полезно для ручного запуска миграций, отладки, проверки файлов и выполнения произвольных команд внутри окружения контейнера.     |

<details>
<summary>Примеры использования Make-команд</summary>

```bash
# Запуск проекта
make start
# => Создаёт и запускает контейнеры в фоновом режиме
# => Первый запуск может занять несколько минут из-за сборки образов

# Просмотр логов (живой поток)
make logs
# => Показывает логи всех сервисов
# => Для логов конкретного сервиса: docker compose logs -f backend

# Перезапуск с полной очисткой
make rebuild
# => ВНИМАНИЕ: удаляет все данные в БД!
# => Используйте только если нужна чистая установка

# Быстрая проверка внутри контейнера
make bash-back
# => Открывает bash в контейнере backend
# => Пример: запустить миграции вручную
(root@backend)$ alembic upgrade head
(root@backend)$ exit
```

</details>

### Запуск без Make

Если Make не установлен, вы можете использовать Docker Compose напрямую:

```bash
# Запуск
docker compose up -d

# Остановка
docker compose down

# Логи
docker compose logs -f

# Полная пересборка
docker compose down -v
docker compose up -d --build

# Shell в контейнере backend
docker compose exec backend bash
```

### Миграции базы данных

Управление схемой БД осуществляется через **Alembic**. Миграции выполняются автоматически при старте backend-контейнера (см. `command` в `docker-compose.yml`), но при необходимости их можно запустить вручную.

В директории `backend/` есть собственный `Makefile` с командами для миграций:

```bash
cd backend

# Накатить все миграции
make migrate

# Откатить последнюю миграцию
make downgrade

# Создать новую миграцию (после изменений в моделях)
make makemigrations m="описание изменений"

# Просмотреть историю миграций
make history
```

Либо напрямую через Docker:

```bash
# Накатить все миграции
docker compose exec backend alembic upgrade head

# Откатить последнюю миграцию
docker compose exec backend alembic downgrade -1

# Создать новую миграцию
docker compose exec backend alembic revision --autogenerate -m "описание изменений"

# Просмотреть историю миграций
docker compose exec backend alembic history
```

Миграции находятся в `backend/alembic/versions/`. Новые файлы создаются автоматически при выполнении `alembic revision --autogenerate`, который сравнивает текущее состояние моделей с реальной схемой БД.

## API

Все эндпоинты API находятся под префиксом `/api`. Система следует REST-конвенции: `GET` для чтения, `POST` для создания, `PUT`/`PATCH` для обновления, `DELETE` для удаления.

| Модуль    | Префикс          | Описание                                                    |
| --------- | ---------------- | ----------------------------------------------------------- |
| Auth      | `/api/auth`      | Регистрация, вход, выход, обновление токенов                |
| Users     | `/api/users`     | Просмотр и редактирование профилей, список пользователей    |
| Articles  | `/api/articles`  | CRUD статей, управление соавторами, загрузка/скачивание PDF |
| Reviews   | `/api/reviews`   | Создание рецензий, изменение статусов, просмотр рецензий    |
| Journals  | `/api/journals`  | CRUD журналов (доступно только ADMIN)                       |
| Citations | `/api/citations` | Подсчёт цитирований, управление ссылками                    |

Детальная документация с примерами запросов и ответов доступна в **Swagger UI** по адресу `http://localhost:8000/docs` после запуска проекта.

## Архитектура

Проект следует слоистой архитектуре **Repository → Service → Router**, где каждый слой имеет чёткую зону ответственности:

- **Repository** — взаимодействие с базой данных через SQLAlchemy. Инкапсулирует SQL-запросы и маппинг моделей.
- **Service** — бизнес-логика. Обрабатывает данные, проверяет условия, координирует несколько репозиториев при необходимости.
- **Router** — HTTP-эндпоинты. Валидирует входящие данные через Pydantic-схемы, вызывает сервисы, формирует ответы.

```
backend/
├── app/
│   ├── core/             # Конфигурация, исключения, зависимости, общие схемы ответов
│   ├── infrastructure/   # Настройка базы данных (SQLAlchemy engine, сессии), Alembic
│   └── modules/
│       ├── auth/         # Аутентификация, JWT-токены, хеширование паролей
│       ├── users/        # Пользователи, профили, ролевая модель
│       ├── articles/     # Статьи, соавторы, согласование, загрузка файлов
│       ├── reviews/      # Рецензирование, статусы рецензий
│       ├── journals/     # Управление журналами
│       └── citations/    # Цитирования и метрики
├── tests/                # Тесты на Pytest
└── alembic/              # Миграции базы данных
```

## Публикационный workflow

Жизненный цикл статьи в системе проходит через несколько обязательных стадий, каждая из которых управляется определёнными правилами доступа и переходов:

```
Черновик (DRAFT)
  │
  │  Автор добавляет соавторов, загружает PDF,
  │  редактирует метаданные статьи
  │
  ▼
Согласование соавторов (PENDING_APPROVAL)
  │
  │  Каждый соавтор подтверждает или отклоняет
  │  текущую версию статьи. До получения всех
  │  согласий статья не может перейти дальше.
  │
  ▼
Рецензирование (REVIEW)
  │
  │  Рецензенты изучают статью и выносят решение:
  │  одобрить, отклонить или запросить доработку.
  │  При запросе доработки статья возвращается
  │  автору на внесение исправлений.
  │
  ├──→ Опубликовано (PUBLISHED)
  │       Статья доступна для чтения и цитирования
  │       всеми пользователями платформы.
  │
  └──→ Отклонено (REJECTED)
          Статья отклонена по итогам рецензирования.
          Автор может создать новый черновик на основе
          отклонённой статьи.
```
